# 完整提交信息规范

每个提交都应使未参与开发的人理解为什么改、改了什么、如何验证，以及如何回滚。标题与正文可以用中文；字段名固定使用下列英文名称，便于自动检查。

## 格式

```text
<type>(<scope>): <具体变化摘要>

Why:
说明问题、触发背景和本次改动的目标。

Changes:
- 列出关键变化及受影响模块。

Validation:
- 记录实际执行的命令、结果、环境，以及未执行的验证及原因。

Risks:
- 写明兼容性、数据影响和回滚办法；风险较低也需交代理由。

Refs:
- Issue / PR / 设计文档；无外部任务时写明任务描述。

Bugfix: docs/bugfixes/YYYY-MM-DD-short-name.md
```

`Bugfix:` 仅在 `fix` 类型时必填，其他类型可以省略。多个缺陷记录可写多行 `Bugfix:`。标题与正文间留空行，正文每个字段都要有实际内容，不能保留模板占位符。`scope` 可省略；建议标题不超过 72 字符。破坏性变更用 `feat(config)!:` 等形式，并追加 `BREAKING CHANGE:` 说明迁移方法。

| type | 用途 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | 修复行为缺陷，必须附记录和单元回归测试 |
| `docs` | 文档变动 |
| `refactor` | 不改变预期行为的结构调整 |
| `test` | 新增或改善测试 |
| `ci` | CI 工作流 |
| `build` | 构建或依赖 |
| `perf` | 性能优化；若同时修复缺陷，使用 `fix` 并附记录 |
| `style` | 格式调整 |
| `chore` | 其他维护任务 |
| `revert` | 撤销既有变更，关联被撤销的提交和原因 |

## 可参考的维护提交

```text
docs(workflow): 明确分支开发和完整提交规范

Why:
维护流程缺少统一提交格式和缺陷记录要求，后续定位问题难以追溯。

Changes:
- 增加贡献指南、提交模板和 bugfix 模板。
- 明确任务分支通过 PR 合并到 main 的步骤。

Validation:
- 人工核对文档命令与仓库入口，检查所有新增本地链接。
- git diff --check 通过。

Risks:
- 仅修改维护文档，不改变存档格式；可通过 revert 回滚。

Refs:
- 维护任务：建立可持续开发和缺陷追踪流程。
```

示例中的结果不能直接复制成实际验证结果。修复提交应额外引用 [bugfix 文档](bugfixes/README.md) 中的真实记录。

## 自动检查

```text
python scripts/check_development_policy.py --base origin/main --head HEAD
```

检查 PR 中所有新增提交（包括开发分支上的合并提交），而非仅最后一条。每条 `fix` 都必须在自己的提交中包含 `Bugfix:` 引用的记录及 `tests/test_*.py` 的新增或修改；不能等到后续提交才补记录。记录中的必需章节也会被检查。

检查读取 Git 提交对象，因此提交前还应检查工作区内容，提交后再运行策略检查。该脚本不修改 Git 配置、提交历史或工作区，也不能判断测试是否确实重现了故障。
