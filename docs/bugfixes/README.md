# Bugfix 记录与处理流程

每个行为缺陷的修复都必须留下长期记录，正文包含**原因、复现步骤、解决方案、单元测试**。Issue 用于收集反馈，本目录保存与代码一起评审和版本化的最终结论；两者不能相互替代。

## 修复流程

1. 从最新 `origin/main` 创建 `fix/<简短主题>` 分支。
2. 复制 [TEMPLATE.md](TEMPLATE.md) 为 `YYYY-MM-DD-short-name.md`。日期为记录创建日期，标题中说明缺陷；不确定的历史发生日期写“未确认”。
3. 记录版本、环境、最小复现、预期与实际结果，分析调用路径和根因，注明证据。
4. 在 `tests/test_*.py` 中新增或修改针对故障的单元测试，用临时目录和合成数据，运行并记录修复前失败的结果。
5. 完成修复，记录设计选择、失败处理和影响范围；同一用例在修复后通过，再执行全量测试。
6. 在一个 `fix` 提交中提交代码、测试、记录与相应 CHANGELOG 条目；正文增加 `Bugfix: docs/bugfixes/实际文件名.md`。PR 中也链接记录。
7. CI 和评审通过后 merge 到 `main`；需要追加实机证据时可另开文档分支补录日期和结果。

针对 Lua、GUI、安装器等缺陷，应尽量提取可测试的逻辑或使用模拟依赖验证契约，再补 Windows / 游戏复现。仅有源码字符串断言或人工截图不足以证明行为修复。确实无法在单元测试中覆盖的部分必须解释边界，并提供可重复的人工步骤；不能用这些说明代替本次修复的单元回归用例。

修复前无法取得旧版本或执行旧环境时，明确写“未执行”及原因，提供现有证据和补验方式；不得编造红灯结果或把当前代码通过写成旧版复现。历史补录同样遵守这一原则。

## 记录规范

- 保留模板中的七个二级标题，填写实际内容，删除占位提示。CI 检查章节和文件关联，内容质量由评审确认。
- 单元测试章节必须包含测试文件、用例名、命令、关键断言、修复前后结果与环境。全量结果另列在验证章节。
- 路径、日志和数据使用通用示例；禁止上传真实世界存档或含个人信息的配置。
- 同一缺陷持续补充同一记录；不同根因创建独立记录。记录关联提交无需写当前提交自身 SHA，可用 PR、版本或 `git log -- <记录路径>` 追踪。
